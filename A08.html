🎯 A08:2025 - Software or Data Integrity Failures Overview

Definition: Weaknesses in software updates, CI/CD pipelines, dependency management, and data validation that allow attackers to inject malicious code or tamper with critical data.

Key Vulnerability Areas

1. Unsigned Software Updates

No cryptographic verification of updates → Attackers inject malware

2. Dependency Tampering

Unverified third-party packages → Supply chain compromise

3. Unsigned Code Commits

No GPG signature verification → Impersonation and code injection

4. Data Tampering

No integrity checks (HMAC/signatures) → Data modification undetected

5. Insecure Deserialization

Untrusted data deserialization → Remote code execution

⚠️ Real-World Impact

SolarWinds (2020): $100M breach via compromised software updates

NotPetya (2017): $10B damage via trojanized software updates

Python Package Attack: Malicious packages targeting typos in dependency names

❌ Scenario 1: Unsigned Software Updates

When software updates are not cryptographically signed, attackers can intercept and modify updates before installation, leading to malware injection.

Vulnerable Implementation

❌ Vulnerable Code (Python) 
def download_update():
    # NO SIGNATURE VERIFICATION!
    response = requests.get('http://updates.example.com/app.exe',
                           verify=False)  # CRITICAL!
    
    # Write directly without checking
    with open('/opt/app/binary', 'wb') as f:
        f.write(response.content)
    
    # Execute update (could be malware!)
    subprocess.run(['/opt/app/binary', '--install'])
    
    return "Update installed"

# VULNERABILITIES:
# 1. HTTP instead of HTTPS
# 2. verify=False ignores SSL errors
# 3. No signature verification
# 4. No checksum validation
# 5. No rollback capability
# Result: Attacker injects malware via MITM attack

Attack Flow:

1. Application checks for updates

2. Attacker intercepts connection (MITM)

3. Attacker returns malicious binary

4. No verification performed

5. Malware installed with app privileges

✅ Secure Implementation

✅ Secure Code (Python) 
import hashlib
from cryptography.hazmat.primitives.asymmetric import padding

TRUSTED_PUBLIC_KEY = "-----BEGIN PUBLIC KEY-----..."

def verify_signature(data, signature):
    """Verify cryptographic signature"""
    try:
        public_key.verify(signature, data, padding.PSS(...), 
                         hashes.SHA256())
        return True
    except:
        return False

def download_update_secure():
    # Use HTTPS with certificate verification
    response = requests.get('https://updates.example.com/app.exe',
                           verify=True)
    
    # Download signature separately
    sig_response = requests.get('https://updates.example.com/app.exe.sig',
                               verify=True)
    signature = sig_response.content
    
    # VERIFY SIGNATURE
    if not verify_signature(response.content, signature):
        raise IntegrityError("Signature verification failed!")
    
    # VERIFY CHECKSUM
    expected_hash = "a3c8d4e9f2b1c7d8e9f0a1b2c3d4e5f6"
    actual_hash = hashlib.sha256(response.content).hexdigest()
    if actual_hash != expected_hash:
        raise IntegrityError("Checksum mismatch!")
    
    # BACKUP current version
    shutil.copy('/opt/app/binary', '/opt/app/binary.backup')
    
    # ATOMIC write
    with open('/opt/app/binary.tmp', 'wb') as f:
        f.write(response.content)
    
    # Move atomically
    os.rename('/opt/app/binary.tmp', '/opt/app/binary')
    
    return "Update verified and installed"

Comparison: What Changed?

Vulnerable ❌

• HTTP connection (no SSL)

• No signature verification

• Direct file write

• No rollback

• No checksums

Secure ✅

• HTTPS with verification

• RSA signature checked

• Atomic file operations

• Backup before update

• SHA256 checksums

🔧 Key Remediation Steps

1. Cryptographic Signatures

Sign all updates with private key, verify with public key

2. Checksum Verification

Calculate and verify SHA256 hash of downloaded file

3. HTTPS & Certificate Pinning

Use HTTPS, pin update server certificate

4. Atomic Operations

Update to temp file first, then atomic move

5. Rollback Capability

Keep backup of previous version

async function loadUserProfileSecure() {
    try {
        const response = await fetch('/api/user/profile');
        const result = await response.json();
        
        const { data, signature, timestamp } = result;
        
        // VERIFY TIMESTAMP (prevent replay)
        const timeDiff = Date.now() - new Date(timestamp).getTime();
        if (timeDiff > 3600000) { // 1 hour
            throw new Error('Data too old - possible replay attack');
        }
        
        // VERIFY HMAC SIGNATURE
        const serverSecret = 'API_INTEGRITY_SECRET';
        const expectedSig = await generateHMAC(data, serverSecret);
        
        if (signature !== expectedSig) {
            throw new Error('Data tampering detected!');
        }
        
        // NOW SAFE TO USE DATA
        const userData = JSON.parse(data);
        document.getElementById('balance').textContent = userData.balance;
        document.getElementById('email').textContent = userData.email;
        
    } catch (error) {
        console.error('Data integrity check failed:', error);
        document.getElementById('error').textContent = 
            'Failed to load data - integrity check failed';
    }
}

How HMAC Protection Works

HMAC (Hash-based Message Authentication Code)

Combines data with secret key to create unforgeable signature

Server-Side:

Server calculates: HMAC = SHA256(data + secret_key)

Sends: data + HMAC signature + timestamp

Client-Side:

Verify: Calculate HMAC with same data

Compare with received signature

If mismatch → Data was tampered

Why It Works:

Attacker can't modify data without knowing secret_key

Attacker can't forge valid HMAC

❌ Scenario 3: Dependency Tampering & Supply Chain Attacks

When dependencies are not pinned to specific versions or verified with checksums, attackers can inject malicious code through compromised or typosquatted packages.

Vulnerable: No Version Pinning

❌ Vulnerable package.json (Node.js) 
{
  "dependencies": {
    "lodash": "*",           // LATEST VERSION - unpredictable!
    "express": "latest",     // No version control
    "axios": "^4.0.0",       // Version range - allows updates
    "moment": "~2.29.0"      // Still allows patch updates
  }
  // NO lock file committed!
}

// Day 1: npm install (gets lodash 4.17.20 - safe)
// Day 2: Attacker publishes malicious lodash 4.17.21
// Day 3: New developer runs npm install (gets malicious version!)
// Day 4: Malware executes in your application
// Result: Supply chain compromise

🔍 What's the Difference?

Vulnerable Approach:

• No version pinning → Different builds on different days

• No lock file → New versions installed automatically

• No checksums → Can't verify package integrity

Secure Approach:

• Exact version pinning → Same build every time

• Lock file with checksums → Verify authenticity

• npm ci command → Uses lock file, not package.json

✅ Scenario 4: Cryptographic Signature Verification

Demonstrates how digital signatures prove authenticity and integrity. This is the core defense against tampering.

How Digital Signatures Work

The Process

1. Signing (Server/Publisher Side):

• Create hash of file: SHA256(file) = HASH1

• Encrypt hash with private key: SIGNATURE = RSA_encrypt(HASH1, private_key)

• Send: FILE + SIGNATURE

2. Verification (Client Side):

• Decrypt signature with public key: HASH2 = RSA_decrypt(SIGNATURE, public_key)

• Calculate file hash: HASH1 = SHA256(file)

• Compare: If HASH1 == HASH2, file is authentic!

Why This Protects You

Even if attacker intercepts:

✅ Can't forge signature (needs private key)

✅ Can't modify file (signature won't match)

✅ Tampering immediately detected

Protects against:

• Man-in-the-middle (MITM) attacks

• Network-level tampering

• Compromised download servers

• Supply chain injection

Real-World Implementation

✅ Signature Verification (.NET Core) 
public class UpdateVerifier {
    private const string TRUSTED_CERT_HASH = 
        "A1B2C3D4E5F6...";  // Pinned certificate
    
    private const string TRUSTED_PUBLIC_KEY = 
        "-----BEGIN PUBLIC KEY-----\nMIIBIjA...";
    
    public bool VerifyUpdate(byte[] updateData, 
                             byte[] signature) {
        try {
            using (var rsa = RSA.Create()) {
                rsa.ImportFromPem(TRUSTED_PUBLIC_KEY);
                
                // Verify RSA signature
                return rsa.VerifyData(
                    updateData,
                    signature,
                    HashAlgorithmName.SHA256,
                    RSASignaturePadding.Pkcs1
                );
            }
        } catch (Exception ex) {
            LogError($"Signature verification failed: {ex}");
            return false;
        }
    }
}

⚠️ Real-World: SolarWinds & Supply Chain Attacks

December 2020: SolarWinds Supply Chain Compromise

Victims: 18,000+ organizations including US Treasury, State Department, Pentagon

Method: Trojaned Orion software update (digitally signed!)

Damage: $100M+ incident response costs

Duration: 8+ months before detection

What Went Wrong

1. Build Pipeline Compromised:

Attacker gained access to SolarWinds' build system

2. Code Injection:

Injected malicious code into Orion software

3. Legitimate Signature:

Build system signed update with REAL SolarWinds certificate

4. Trust Exploited:

Customers trusted the signature - installed malware

5. Backdoor Established:

SUNBURST malware gave attacker persistent access

Key Lessons

1. Secure Your Build Pipeline

Code signing only protects if build system is secure

If pipeline is compromised, attacker can sign malware legitimately

2. Defense in Depth

Don't rely on signatures alone

Add: Code review, integrity checks, monitoring, testing

3. Monitor Execution Behavior

Even legitimate software can have suspicious behavior

Monitor: Network connections, file access, process creation

4. Incident Response

Fast detection and response minimizes damage

SolarWinds undetected for 8+ months = huge breach

How to Prevent Similar Attacks

✅ Build System Security

Access control, audit logging, isolated build environment

✅ Code Review

All changes reviewed before merge, signed commits

✅ Artifact Signing

Sign build artifacts, verify before deployment

✅ Dependency Verification

Pin versions, verify checksums, scan for vulnerabilities

✅ Runtime Monitoring

Detect suspicious behavior during execution

✅ Incident Detection

Fast response to anomalies, threat hunting
